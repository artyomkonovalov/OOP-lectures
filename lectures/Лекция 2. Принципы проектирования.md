# Принципы SOLID

<a name="section-002"></a>

## 1. S - single responsibility principle (SRP)
* проектирование типов таким образом, что они имеют единственную причину для изменения

<a name="section-003"></a>

### Причины нарушения
* "простота" (топорность) - нет необходимости в абстракциях, низкий порог для онбординга
*  переиспользование логики - часто логика в типах, не соблюдающих SRP имеет общие части, вызвать приватный метод типа в нескольких местах проще, чем реализовать грамотную декомпозицию


<a name="section-004"></a>

### Проблемы от нарушения
* сильная связанность реализации различных бизнес-требований
	* загрязнённость IntelliSense
	* усложнение тестирования
* усложнённая кастомизация отдельных реализаций - изменения в общем коде могут поломать другие решения


<a name="section-005"></a>

### Как определить
1. Наличие несвязанной логики в одном типе
2. наличие нескольких разных способов делать одно и то же в одном типе
3. сильное различие в наборе данных для выполнения операции
4. сильное различие в наборе зависимостей для выполнения операций
> Один тип берёт на себя ответственность нескольких типов


<a name="section-006"></a>

### Как исправлять
1. Декомпозиция: один класс --> несколько классов
2. Полиморфизм - выделяем абстракцию и делаем разные классы с единым интерфейсом


<a name="section-007"></a>

### Преимущества соблюдения
* Более чёткая объектная модель
* Изоляция различных частей логики
* Меньше вероятность оказать влияние на другие реализации при внесении изменений
* упрощение модульного тестирования


<a name="section-008"></a>

## 2. Open/Closed principle (один из самых важных) (OCP)
* логика должна быть открытой для расширения, но закрытой для изменения
* проектирование типов таким образом, что их логику можно расширить, не изменяя исходный код


<a name="section-009"></a>

### Причины нарушения
* Некорректное разделение логики/выделение абстракций
* Итеративная разработка без учёта общей картины 


<a name="section-010"></a>

### Проблемы от нарушения
* Большая связанность логики
* Большая вероятность повлиять на другие реализации
* Сложнее модульное тестироваие
> Нет возможности протестировать конкретную реализацию изолировано


<a name="section-011"></a>

### Как определить
1. SRP - про типы, OCP - про реализации
	* нарушение SRP на уровне реализации (метода) = нарушение OCP
2. Представить, что разрабатываем библиотеку
	* можно добавить без изменения новый функционал => соблюдается


<a name="section-012"></a>

### Как исправить
1. выделение абстракций
	* определить область вариативности в коде
	* выделить для неё интерфейс
2. полиморфизм
3. декомпозиция

<a name="section-013"></a>

### Преимущества
1. Изоляция реализаций
2. Возможность расширения логики без влияния на другие реализации
3. Упрощение модульного тестирования

<a name="section-014"></a>

## 3. L - Liskov substitution principle (LSP)
* проектирование иерархий типов таким образом, чтобы логика дочерних типов не нарушала инвариант родительских

<a name="section-015"></a>

### Нужен для:
* Создание корректных иерархий
* Правильное наследование

<a name="section-016"></a>

### Причины нарушения
* Плохое понимание правил наследования
* Попытка отражения фактических иерархий в объектной модели
	* объектная модель должна отражать предметную область
	* объектная модель должна быть приближена к предметной области
	* реализм != хороший код
	* подходы проектирования > попадание 1в1 в предметную область

<a name="section-017"></a>

### Проблемы
* Сильная связанность между разными уровнями иерархий
	* (наличие уровней иерархий в принципе)
* Возникновение special-case в бизнес-логике
	* общая абстракция может быть корректна с точки зрения предметной области, но не корректна с точки зрения существующей бизнес-логики
* Нарушение OCP

<a name="section-018"></a>

### Как определить
1. Реализация не соответствует ожиданиям поведениям
	1. неочевидная логика
	2. исключения где не надо
2. Костыли над полиморфизмом
3. Неявные связи между типами в иерархии
4. "Общие поведения" не присущие всем дочерним типам


<a name="section-019"></a>

### Как исправить
1. ре-моделирование иерархии
2. использование feature-интерфейсов

<a name="section-020"></a>

### Преимущества
1. Явность реализации
2. Более низкая связанность между базовыми и конкретными типами
3. (негласно) Нет отвратительно плохой иерархии в системе

<a name="section-021"></a>

## 4. I - interface segregation principle


<a name="section-022"></a>

### Правило для
* корректного проектирования интерфейсов


<a name="section-023"></a>

### Проблемы
* абстракции обрастают лишними, ненужными для всех её пользователей поведениям
* большее пространство для ошибок
* нарушение SRP для реализаций


<a name="section-024"></a>

### Как определить
* ISP - SRP для интерфейсов


<a name="section-025"></a>

### Преимущества
1. соблюдение SRP для реализаций
2. отсутствие лишнего функционала при работе с объектами абстракции
	* меньше протечки деталей реализации
3. большая модульность
	* после декомпозиции интерфейсов их может реализовывать один типа
	* а может несколько
	* а может одну часть один, а другую - другой

<a name="section-026"></a>

## 5. Dependency inversion principle
* проектируем типы так, чтобы не было реализаций, зависящих друг от друга

<a name="section-027"></a>

### Виды абстракций
1. Верхнеуровневая / низкоуровневая
	* Разница в логическом отношении между функционалом
	* низкоуровневая - бизнес правила, которые могут быть переиспользованы
	* высоуровневая - использование низкоуровневой, оркестровая
2. бизнесовая / инфраструктурная
	* разница в назначении абстракции
	* бизнесовая - отражает бизнес-логику
	* инфраструктурная - ...

<a name="section-028"></a>

### Примеры нарушений
* Return-type

<a name="section-029"></a>

### Чуть глубже чем кажется
* нарушение этого принципа не обязательно происходит при явных связях
	* излишняя связь не на уровне связей между типами, а на уровне реализации
	* методы одного типа реализованы в соответствии с логикой другого типа

<a name="section-030"></a>

### Проблемы
1. Сильная связанность между абстракциями различного уровня/назначения
2. Детали реализации одной абстракции начинают влиять на другую
	* больше вероятность что-то сломать
3. Усложнение модульного тестирования
	* отсутствие возможности использовать mock-объекты

<a name="section-031"></a>

### Как определить
1. Явные связи между реализациями разного уровня/назначения
	1. важно: связи, которых не должно быть
	2. данный принцип не означеет, что везде должны быть интерфейсы
2. Неявные связи между различными реализациями
	1. Если код в одно месте написан с расчётом на реализацию в другом месте
3. Наличие связей между абстракцией и реализацией


<a name="section-032"></a>

### Как исправить
1. выделение абстракций / репроектирование абстракций
2. декомпозиция

<a name="section-033"></a>

### Преимущества
1. Большая гибкость при расширения
2. Соблюдение OCP


<a name="section-034"></a>

# Принципы GRASP

<a name="section-035"></a>

## 1. Information expert
* Информация обрабатывается там, где она используется

<a name="section-036"></a>

### Нужен для
* корректной инкапсуляции логики
* помогают ответить на вопрос "а где это должно делаться?"

<a name="section-037"></a>

### Проблемы при нарушении
1. Нарушение SRP
2. Проблемы с переиспользованием
	* либо копипаста
	* либо нелогичная связь между модулями
3. Усложнённое тестирование


<a name="section-038"></a>

### Как определить нарушение
* "анемичные модели" - есть данные, но никакой логики
* перегрузка логикой
	* god-object/god-type - антипаттерн, один тип занимается реализацией всего
	* один тип напрямую работает с данными большого количества других типов
* дубликация логики

<a name="section-039"></a>

### Как исправить
1. "логика должна находиться там, где находится минимально полный набор данных, необходимый для её реализации"
2. т. е. инкапсулировать логику в типах, хранящих данные

<a name="section-040"></a>

### Преимущества
1. Большая модульность логики
	* проще переиспользовать
	* проще изолированно тестировать
2. Соблюдение SRP

<a name="section-041"></a>

## 2. Low coupling and High cohesion
* coupling - мера зависимости модулей друг между другом
* cohesion - мера логической соотнесённости логики в рамках модуля
* Все методы класса должны быть соотнесены с данными, который класс содержит (не значит, что в классе должен быть только один метод)

<a name="section-042"></a>

## 3. Indirecion
* object indirection - любое взаимодействие с данными, поведениями, модулями, реализованное не напрямую, а через какой-либо агрегирующий их объект
* interface indirection - любое взаимодействие с данными, поведениями, модулями, реализованное не напрямую, а через какой-либо агрегирующий их интерфейс

<a name="section-043"></a>

## 4. Protected variations
* коррелирует с OCP из SOLID - делает больший акцент на определение точек нестабильности
* подразумевает выделение стабильного интерфейса над нестабильной реализацией

<a name="section-044"></a>

## 5. Pure fabrication
* подразумевает наличие в системе искусственной, выдуманной сущности, не отражающей конкретный объект моделируемых бизнес процессов
* обычно это инфраструктуры модули, сервисы
* не рекомендуется вносить такие типы в доменную модель
