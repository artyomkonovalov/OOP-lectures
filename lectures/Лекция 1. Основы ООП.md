# Введение

<a name="section-002"></a>

## Зачем нужно проектирование?

<a name="section-003"></a>

### Изначальная разработка 
Разработка "с чистого листа" - процесс с минимальной сложностью
- нужно продумать, что хотим сделать
- нужно подумать, как хотим сделать
- можно менять всё, что есть
- нет риска сломать существующую логику / данные (их нет)

<a name="section-004"></a>

### Поддержка
Проблемы:
- Потеря контекста функционала:
	- устаревает документация
	- память человека не так надёжна
- Потеря технического контекста:
	- разработка - про компромиссы
	- на реализацию может влиять текущая ситуация. В будущем рационализация может исчезнуть - решения станут непонятными

<a name="section-005"></a>

### Доработка функционала
преследуем 2 цели:
- основная - добавить новый функционал
- главная - не сломать существующий
Цель хорошей архитектуры - не столько упростить корректные доработки, сколько усложнить некорректные.

<a name="section-006"></a>

#### Расширение vs Изменение
- Расширение - добавление нового способа делать уже существующее действие
- Изменение - добавление в принципе нового функционала
Хороший дизайн может усложнять внесение изменений

<a name="section-007"></a>

### Простота != Топорность
Нужно правильно расставлять приоритеты: цель - сделать так, чтобы код было просто понять через 2 года, а не так, чтобы его было просто написать.
Если в коде не отражено представление системы, то другому человеку / нам через пару лет придётся заново восстанавливать идею - и это может получиться неверно

<a name="section-008"></a>

#### Топорный код
- не содержит абстракций
- не "переусложнён"
- НО: не имеет структуры и не помогает в нём разобраться

<a name="section-009"></a>

#### Простой код:
- может нести за собой дополнительную когнитивную нагрузку
- НО: более структурирован
	- позволяет взглянуть на логику на разных уровнях
	- отражает намерения разработчика
	- progressive disclosure контекста системы - поэтапное раскрытие информации - стратегия проектирования интерфейсов, при которой пользователю в каждый момент времени показывают только самые важные и нужные данные / функции, а сложные, расширенные или второстепенные опции скрывают до тех пор, пока она не понадобится

<a name="section-010"></a>

## Парадигмы программирования
- набор правил для решения определённых проблем
- набор ограничений, отбирающих у нас определённые свободы при выборе решения (это хорошо)

<a name="section-011"></a>

### Процедурное программирование
Код разбит на функции и процедуры, которые последовательно(!) обрабатывают данные

<a name="section-012"></a>

### Структурное программирование
Развитие процедурного подхода с использованием циклов и ветвлений вместо хаотичных переходов

<a name="section-013"></a>

### Объектно-ориентированное программирование
Объединение данных и функций для их обработки в единые сущности - объекты

<a name="section-014"></a>

# Основные концепции ООП

<a name="section-015"></a>

## Инкапсуляция
принцип объединения атрибутов и поведений (данных и методов) в рамках одного типа
**Тип** - *шаблон*, описывающий, какие данные и методы имеет объект
**Объект** - *экземпляр* типа, существующий во время выполнения кода, занимающий память
Инкапсуляция:
1. Забирает свободу размещения логики
	- логика не должна жить сама по себе
	- логика должна принадлежать типу
2. Заставляет моделировать логику в виде сущностей
	- приводит к более детальному продумыванию дизайна
	- приводит к более чёткому отражению намерения автора кода
3. Заставляет столкнуться с проблемой связей между данными / сущностями / логикой
	- если не продумать связи грамотно, модель превратиться в кашу
	- без выделения объектной модели, связи всё ещё существуют, но они неявные (что хуже)
4. Локализует логику, работающую с одним набором данных

<a name="section-016"></a>

### Инвариант данных
набор правил, определяющих корректное состояние данных

<a name="section-017"></a>

### Инвариант типа
набор данных, их инварианта и поведений, позволяющих изменять эти данные согласно их инварианту

<a name="section-018"></a>

## Сокрытие
- отбирает свободу доступа к данным / поведениям
- **Модификаторы доступа** позволяют ограничить доступ к данным и методам:
	- `public` - доступ отовсюду
	- `private` - доступ только внутри типа
	- `protected` - доступ внутри типа и у дочерних типов
	- `internal` - доступ только в рамках текущей сборки (использование для обеспечения сокрытия в бизнес логике свидетельствует о неправильно выстроенной абстракции)

<a name="section-019"></a>

## Абстракция = инкапсуляция + сокрытие
- объединяя инкапсуляцию и сокрытие мы можем гарантировать соблюдение инварианта типа
- представляет собой "чёрный ящик" с  точки зрения реализации
- позволяет писать более простой код на более высоких уровнях абстракции
- хороший дизайн - локальные, самодостаточные абстракции + их комбинация на уровне выше

<a name="section-020"></a>

## Композиция
способ создания одних типов на основе других, при помощи хранения объектов одних типов в объектах других типов

<a name="section-021"></a>

### Виды композиции

<a name="section-022"></a>

#### Агрегация
вид композиции, подразумевающий, что хранимые значения получаются извне
- более низкая связанность между вложенными и содержащими типами
- мы не определяем, как создаются вложенные объекты

<a name="section-023"></a>

#### Ассоциация
вид композиции, подразумевающий, что хранимые значения создаются самим объектом
- более высокая связанность  между вложенными и содержащими типами
- мы сами создаём вложенные объекты

<a name="section-024"></a>

## Полиморфизм
подразумевает, что логика, написанная один раз, может выполняться по-разному. В контексте ООП - полиморфизм подтипов. Больше отделяем абстракцию от реализации. В C# полиморфизм реализуют наследование, а так же интерфейсы, которые определяют контракт - какие у типа должны быть методы, свойства.
- интерфейсы позволяют лучше структурировать вариативность логики
- полиморфизм позволяет избежать излишней условной логики
- полиморфизм позволяет моделировать вариативность логики представлением субъектов предметной области в виде типов, реализующих соответствующие им поведения
- полиморфизм отнимает свободу реализации вариативности логики

<a name="section-025"></a>

#### Полиморфизм подтипов
отделение абстракции от реализации, позволяющее прозрачно использовать различные реализации посредством единого контракта

<a name="section-026"></a>

### Реализация (наследование поведений)
используются интерфейсы, в C# реализовывать интерфейсы могут как классы, так и структуры. Говорят, что тип реализует интерфейс.

<a name="section-027"></a>

## Наследование
- наследование в C# поддерживают только классы
- в отличие от интерфейсов получаем и реализации базового класса
- дочерние классы могут переопределять реализации родительских классов

<a name="section-028"></a>

#### Виртуальные методы:
- имеют реализацию в базовом классе
- могут быть переопределены в наследнике
- наследники могут не переопределять - будет использоваться базовая реализация
- определяется в обычных классах

<a name="section-029"></a>

#### Абстрактные методы
- не имеют тела и реализации в базовом классе
- обязательно должны быть переопределены в наследниках
- объявляется только в абстрактных классах
- нельзя создать экземпляр абстрактного класса

<a name="section-030"></a>

### Наследование (наследование реализаций)
используются базовые классы. В C# одна структура не может быть унаследована от другой или от класса. Говорят, что класс является *наследником* другого класса или его *подклассом*.

<a name="section-031"></a>

### Указания
- использовать для реализации полиморфизма
- не использовать для переиспользования бизнес логики
- наследование приводит к сильной связанности между типами
	- со временем становится сложнее разорвать эту связь
	- код становится сложнее рефакторить
- Применение наследования для переиспользования данных - плохо
- Для переиспользования логики следует использовать композицию

<a name="section-032"></a>

## Объект
совокупность атрибутов и поведений, реализация и данные которого скрыты от его конечного пользователя

<a name="section-033"></a>

## Проектирование объектной модели

<a name="section-034"></a>

### Иммутабельность
свойство данных, не подразумевающее изменения. В ООП используется в виде сокрытия мутабельных данных и иммутабельность значений, не требующих изменения

<a name="section-035"></a>

### Протёкшая абстракция
абстракция, для работы с которой необходимо иметь знание о деталях её реализации

<a name="section-036"></a>

### Обработка ошибок
Способы:
- bool флаги
- исключения
- result types

<a name="section-037"></a>

#### Исключения
- не отражены в сигнатуре
- поиск конкретного типа исключения и ситуации, когда оно кидается, приводит к протёкшей абстракции
	- при работе с интерфейсами всё становится ещё хуже
- неудачное выполнение операции != исключительная ситуация

<a name="section-038"></a>

#### Result types
- выражаем результат операции как объект, тип которого учитывает как успех, так и негативные исходы
- основывается на концепции суммы типов / union-типов
- используются закрытые иерархии, где каждый тип - отдельный исход
- возвращаемый тип - часть сигнатуры (не нужно лезть в детали, чтобы узнать возможные исходы)
- усиление контракта интерфейса (зашиваем поддерживаемые для расширения исходы операции)
- добавление новых исходов возможно, но оно сложнее - меньше вероятность ломающих изменений

<a name="section-039"></a>

##### Анти-паттерны результатов
- Избыточность кейсов результата
	- Кейсы должны выделяться под потенциальные точки вариативности логики, а не под все места в коде, где возвращается ошибка
- Агрегация кейсов результата
	- метод может вызвать несколько операций, возвращающих разный результат
	- если результат метода содержит сумму результатов вызываемых методов - абстракция протекла, сильна связанность
	- ещё хуже, когда результат собирает все кейсы всех реализаций интерфейсов - повод пересмотреть абстракцию

<a name="section-040"></a>

#### Value objects
- **Primitive obsession** - ситуация, когда доменные примитивы выражаются примитивами языка.
- Доменные примитивы могут иметь более узкую область допустимых значений в сравнении с примитивами языка
- Результат - дублирующиеся валидации
Решение - выделение абстракций для доменных примитивов - value objects
- инкапсулируют валидацию в отдельный тип
- при использовании в коде знаем, что валидация пройдена
- если бы она не прошла, объект бы не создался
- ошибка валидации - исключительная ситуация (кидаем исключение в конструкторе)
